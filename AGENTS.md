# AutoDater contributor guidance

## Project overview

AutoDater is an Obsidian community plugin written in TypeScript. It adds and updates YAML frontmatter properties on Markdown notes:

- `Created` is written when a new note has no existing creation property.
- `Updated` is written after a note is modified, using a six-second debounce.
- Existing values are preserved according to the behavior documented in `README.md`.

The supported Obsidian version is defined by `manifest.json` (`minAppVersion`) and the Obsidian package version in `package.json`. Check both before changing plugin API usage.

## Before changing code

- Read the relevant sections of `README.md` before changing user-visible behavior, settings, date formats, or installation/build instructions.
- Treat `manifest.json`, `package.json`, and `tsconfig.json` as the authoritative project configuration.
- For Obsidian API changes, consult the official Obsidian plugin API documentation and the installed `obsidian` type definitions. Do not apply Expo or React conventions to this project.
- Inspect existing TypeScript patterns in `main.ts`, `settings.ts`, and `date-utils.ts` before introducing new abstractions.

## Project structure

- `main.ts` — plugin lifecycle, vault event handlers, and frontmatter updates.
- `settings.ts` — settings types, defaults, validation, persistence parsing, and settings UI definitions.
- `date-utils.ts` — supported date-format implementations.
- `styles.css` — plugin styles, when needed.
- `main.js` — generated production bundle; do not edit by hand.
- `manifest.json` — Obsidian plugin metadata and minimum app version.
- `versions.json` — maps plugin releases to their minimum Obsidian versions.
- `version-bump.mjs` — updates release metadata during `npm version`.
- `assets/` — README and release assets.

## Development and verification

Install dependencies and build the plugin with:

- `npm install`
- `npm run build`

`npm run build` runs TypeScript type-checking and creates the production bundle. Run it after every implementation change. Use `npm run dev` for the esbuild watch build when iterating locally.

When behavior changes, update or add focused tests if a test setup is introduced; otherwise verify the affected behavior manually in an Obsidian test vault and document the verification in the change summary. At minimum, check Markdown filtering, existing frontmatter preservation, case-insensitive property matching, settings parsing, and the relevant date format when those areas are changed.

## Implementation conventions

- Keep TypeScript strict and preserve the existing tab indentation and line-ending conventions.
- Keep date formatting pure and isolated in `date-utils.ts`.
- Validate unknown persisted settings before merging them into defaults.
- Avoid unnecessary frontmatter writes and preserve existing property names and values where the current behavior requires it.
- Handle Obsidian event payloads defensively; only Markdown `TFile` instances should be modified.
- Keep `main.js` out of source edits. It is ignored by Git and generated by the build.
- Keep dependencies minimal. If a dependency is needed, update `package.json` and `package-lock.json` together.

## Release metadata

The version in `package.json` must stay consistent with `manifest.json` and `versions.json`. Use the existing `npm version` lifecycle and `version-bump.mjs` rather than editing release metadata inconsistently. Confirm the resulting metadata and run `npm run build` before a release.

## Git and planning rules

- Use Conventional Commits: `type(scope): description` (for example, `feat(date): add timezone-aware formatting`).
- Do not run `git commit`, `git commit --amend`, `git push`, or `gh pr create` without explicit user approval.
- Before requesting approval, show `git status`, the relevant diff, and the proposed commit message.
- Plan work as logical, atomic, buildable chunks. Label chunks `Chunk 1a`, `Chunk 1b`, `Chunk 2a`, and so on; each chunk should correspond to one reviewable change and one proposed commit.
- This repository does not currently contain `docs/mvp.md` or `docs/roadmap.md`. Do not invent or require those files unless the project owner adds them. Track plans in the task context and keep documentation changes with the implementation they describe.
